# Privacy Baseline — from Phase 1

## The problem this document exists to prevent

It is tempting to say "Phase 1 has no cookies, so privacy is a Phase 5 topic." That is wrong. Even with no cookies and no identifiers, an ad request necessarily carries:

```text
IP address            (from which coarse geo is derived)
User-Agent            (device type, OS, browser)
Referrer / page URL   (what the user is reading)
Timestamp
```

That is personal data processing under most modern privacy regimes. The correct position is not "no privacy work yet" but "a small, explicit baseline from day one, expanded when monetisation or data use requires it."

---

## Phase 1 Production baseline

| Requirement | Implementation |
|---|---|
| **Privacy notice** | A short, honest page on the publisher site describing what is collected, why, and for how long. Linked from the footer |
| **No non-essential cookies** | Phase 1 sets no cookies at all. Nothing to consent to, and we can say so accurately |
| **No persistent advertising identifier** | No cookie ID, no local-storage ID, no fingerprinting, no probabilistic ID |
| **Do not persist raw IP** | IP is used in-request to derive country, then discarded. If any IP-derived value is stored, it is truncated or hashed with a rotating salt, and the reason is documented |
| **Coarsen device and geo** | Store country only — not region, city, or coordinates. Store a device-type enum — not the raw User-Agent string |
| **Short retention** | Raw event data retained 90 days, then aggregated and the raw records deleted. Logs 7 days |
| **Document every field** | A field-level table in the repo: field, source, purpose, retention, whether it is stored. New fields require a row before they are collected |
| **Data minimisation as a default** | If a field is not used by a decision or a report, it is not collected |

**CMP, TCF and GPP are deliberately deferred** — not because privacy is deferred, but because those frameworks exist to communicate consent signals to third parties in a programmatic supply chain, and Phase 1 has no third parties and no consent-dependent processing. They become required when monetisation, external demand, or user-level data use begins. See [standards-status.md](standards-status.md).

## The frequency-cap contradiction, resolved

Frequency capping requires per-user state. Per-user state requires an identifier. So "implement frequency capping in Phase 2 production" and "introduce no identifier until Phase 5" cannot both be true.

**Resolution: Option A — frequency capping is a Lab feature in Phase 2.**

```text
Lab (Environment A)
  synthetic_user_id generated by the traffic simulator
  fully persistent, fully inspectable, zero privacy exposure
  -> we learn the mechanics, the cost, the state-management problem,
     and what breaks when the identifier is unstable

Production (Environment B), Phase 1-2
  no persistent advertising identifier
  no cross-request frequency capping
  where per-page repetition control is needed, it is done in-page,
  in-memory, for that page view only
```

**When we want frequency capping in production**, that is a deliberate, gated decision — Option B:

```text
1. Define the identifier: first-party, our own domain, single-site scope
2. Write down its purpose, lifetime, and scope before implementing it
3. Update the privacy notice
4. Decide whether it is strictly necessary (and therefore consent-exempt
   in the relevant jurisdictions) or requires consent -- and if consent
   is required, build the consent mechanism first
5. Only then implement
```

The point of doing it this way is that **introducing an identifier is an architectural and legal decision, not a feature toggle.** Experiencing that gate is itself part of the learning.

## What we will not do

```text
No fingerprinting, including "probabilistic" identity
No third-party cookies or third-party pixels
No sharing of request data with any external party in Phase 1-2
No collection of any special-category data
No tracking designed to be difficult for a user to see or avoid
```

## To verify before Phase 6 (real monetisation)

Flagged, not assumed — these need checking against actual obligations, and at least the first two warrant professional advice:

* **Israeli Privacy Protection Law, Amendment 13** — in force since August 2025. Its registration, DPO, and notification obligations apply to our own data processing and need to be assessed properly.
* **GDPR** applicability if the site receives EU/EEA visitors and processing purposes expand.
* Whatever the specific monetisation partner's policies require — which is often stricter than the law.
